## Work Package WP01: Health Checks & Kubernetes Probes (Priority: P1)

**Goal**: Implement binary health checks (healthy/unhealthy) for critical dependencies with Kubernetes-compatible liveness and readiness probe endpoints. Addresses User Story 1 (P1) and User Story 4 (P2).

**Independent Test**: Deploy pod with health endpoints, simulate database connection failure, verify Kubernetes restarts pod (liveness) and removes pod from service rotation (readiness). Query `/health/ready` with Redis disconnected, verify response includes `{"checks": {"database": true, "cache": false, "queue": true}}`.

**Prompt**: `tasks/planned/WP01-health-checks-kubernetes-probes.md`

### Included Subtasks

- [ ] **T001** [P] Create Django app `src/observability/` with `__init__.py`, `apps.py`, `README.md`
- [ ] **T002** [P] Create `src/observability/health.py` with `HealthCheckResult` dataclass and `HealthCheck` Protocol
- [ ] **T003** [P] Create `src/observability/utils.py` with `timeout()` context manager (500ms enforcement)
- [ ] **T004** Implement health check registry (`HEALTH_CHECKS` dict) in `health.py` with `register_health_check(name, check, critical=True)`
- [ ] **T005** [P] Create `src/observability/checks/__init__.py` module
- [ ] **T006** [P] Implement `DatabaseHealthCheck` in `src/observability/checks/database.py` (FR-003: PostgreSQL connection check)
- [ ] **T007** [P] Implement `CacheHealthCheck` in `src/observability/checks/cache.py` (FR-003: Redis cache check, **non-critical**)
- [ ] **T008** [P] Implement `QueueHealthCheck` in `src/observability/checks/queue.py` (FR-003: Redis queue/Celery broker check, **critical**)
- [ ] **T009** [P] Implement `MigrationHealthCheck` in `src/observability/checks/migrations.py` (FR-003: pending migrations + running migrations detection)
- [ ] **T010** Create `/health/live` Django view in `health.py` returning 200 if process alive (FR-001)
- [ ] **T011** Create `/health/ready` Django view in `health.py` returning 200 only if critical checks pass (FR-002, FR-004)
- [ ] **T012** Add URL routing for `/health/live` and `/health/ready` in `src/config/urls.py`
- [ ] **T013** Configure settings namespace `OBSERVABILITY_HEALTH_CHECKS_ENABLED` in `src/config/settings/base.py`
- [ ] **T014** Auto-register default health checks in `src/observability/apps.py` `ready()` method

### Constitutional Alignment
- **Principle II (Architecture)**: Health Check Protocol with registry pattern enables downstream extension
- **Principle V (Security)**: Health endpoints public (K8s requirement) but minimal data exposure
- **Principle VI (Performance)**: <100ms per check, 500ms total timeout (FR-005)

### Implementation Notes
- Use `HealthCheckResult(name, status, latency_ms, details)` for all check returns
- Timeout wrapper must catch `TimeoutError` and return `status=False`
- Migration detection: Query `django_migrations` table for locks or running executors (Clarification #1)
- Redis cache/queue separation: Report as separate keys in `checks` object (Clarification #4)

### Parallel Opportunities
- T002/T003/T005 can proceed in parallel (different files)
- T006/T007/T008/T009 can proceed in parallel (independent check implementations)

### Dependencies
- None (foundational work package)

### Test Scenarios (T014)
- **Scenario 1**: Simulate database connection failure (disconnect PostgreSQL), verify `/health/ready` returns 503 with `{"status": "unhealthy", "checks": {"database": false, "cache": true, "queue": true, "migrations": true}}`
- **Scenario 2**: Query `/health/live` with all dependencies down, verify returns 200 OK (liveness ignores dependencies)
- **Scenario 3**: Verify Kubernetes removes pod from service rotation within 1 readiness probe cycle when database fails

### Risks & Mitigations
- **Health check itself crashes**: Wrap check logic in try-except; return 503 with minimal error (no stack traces)
- **Timeout precision**: Use `signal.alarm()` (Unix) or `threading.Timer()` (cross-platform) with 500ms granularity
- **Migration lock detection**: Test with concurrent migrations running to ensure accurate detection

## Work Package WP02: Structured Logging & Correlation IDs (Priority: P2)

**Goal**: Implement structured JSON logging with PII redaction, correlation ID propagation, and secure field filtering. Addresses User Story 2 (P2) and FR-006 to FR-008.

**Independent Test**: Trigger log event with user email and API key in context, verify JSON output contains correlation ID and severity level, and verify PII fields are redacted (e.g., `user_email: "[REDACTED]"`). Test correlation ID propagation from HTTP request → log → Celery task → task log.

**Prompt**: `tasks/planned/WP02-structured-logging-correlation-ids.md`

### Included Subtasks

- [ ] **T015** [P] Create `src/observability/logging.py` module
- [ ] **T016** [P] Create `contextvars.ContextVar` for correlation ID storage in `logging.py`
- [ ] **T017** Implement `JSONFormatter` class extending `logging.Formatter` with required fields (timestamp, severity, message, correlation_id, context)
- [ ] **T018** Implement `PIIRedactionFilter` class extending `logging.Filter` (FR-007: auto-redact `password`, `secret`, `token`, `api_key`, `ssn`, `email`, `phone_number`, `credit_card`)
- [ ] **T019** Create `CorrelationIDFilter` class to inject correlation ID from contextvar into log records
- [ ] **T020** [P] Create `src/observability/middleware.py` module
- [ ] **T021** Implement `CorrelationIDMiddleware` to extract `X-Correlation-ID` header or generate UUID (FR-008)
- [ ] **T022** Store correlation ID in contextvar in middleware
- [ ] **T023** Configure Django `LOGGING` settings in `src/config/settings/base.py` with `JSONFormatter` and filters
- [ ] **T024** Add `OBSERVABILITY_LOGGING_JSON` and `OBSERVABILITY_PII_REDACTION_ENABLED` settings
- [ ] **T025** Configure log severity levels (DEBUG, INFO, WARNING, ERROR, CRITICAL) per FR-016
- [ ] **T026** Update middleware list in settings to include `CorrelationIDMiddleware` (early in middleware stack)
- [ ] **T027** Implement SQL query parameter stripping for FR-015 (parameterized query placeholders only)

### Constitutional Alignment
- **Principle V (Security)**: No PII, secrets, or sensitive data in logs; redaction enforced at emission time
- **Principle VI (Performance)**: <1ms log emission overhead; JSON formatting async-friendly
- **Principle III (Code Quality)**: Type hints for all logging interfaces

### Implementation Notes
- Use stdlib `logging` with custom formatter (Research Decision #1: no structlog dependency)
- Redaction precedence: Explicit rules > pattern matching > field name heuristics
- Correlation ID format: UUID v4 (36 characters, hyphenated)
- PII redaction applied to `context` and `exception` fields before JSON serialization
- SQL parameter stripping: Regex-based replacement `WHERE user_id=123` → `WHERE user_id=?`

### Parallel Opportunities
- T015/T020 can proceed in parallel (different modules)
- T016/T017/T018/T019 can proceed in parallel within `logging.py` (independent classes)

### Dependencies
- None (can proceed in parallel with WP01)

### Risks & Mitigations
- **PII false negatives**: Provide extension point for downstream products to add custom redaction rules
- **Performance overhead**: Benchmark JSON serialization; ensure <1ms per log event at 10k req/min
- **Async safety**: Use `contextvars` (not thread-local) for correlation ID storage

## Work Package WP03: Metrics & B15 Task Observability (Priority: P1)

**Goal**: Implement metric hooks (counters, histograms, gauges) with Prometheus exporter, B15 task observability integration, and pluggable exporter architecture. Addresses User Story 3 (P1), User Story 5 (P3), and FR-009 to FR-014.

**Independent Test**: Schedule Celery task via B15, verify metric hooks emit `task_started`, `task_completed`, `task_duration_seconds` events to Prometheus `/metrics` endpoint. Query Prometheus scraper, verify metrics include `http_requests_total`, `tasks_queue_depth`, and all metrics follow Prometheus naming conventions.

**Prompt**: `tasks/planned/WP03-metrics-b15-task-observability.md`

### Included Subtasks

- [ ] **T028** [P] Create `src/observability/metrics.py` module
- [ ] **T029** Define `MetricCollector` Protocol with `increment()`, `observe()`, `set_gauge()` methods
- [ ] **T030** Implement metric collector registry (`METRIC_COLLECTORS` dict) in `metrics.py`
- [ ] **T031** [P] Create `src/observability/exporters/__init__.py` module
- [ ] **T032** [P] Create `src/observability/exporters/base.py` with `MetricCollector` Protocol definition
- [ ] **T033** [P] Implement `PrometheusCollector` in `src/observability/exporters/prometheus.py` wrapping `prometheus_client.Counter`, `.Histogram`, `.Gauge`
- [ ] **T034** Add `prometheus-client` to `requirements/base.txt` with version pinning
- [ ] **T035** Create `/metrics` Django view in `metrics.py` exposing Prometheus exposition format (FR-012)
- [ ] **T036** Add URL routing for `/metrics` in `src/config/urls.py`
- [ ] **T037** Implement metric label cardinality validation (FR-013: max 100 unique values per label key)
- [ ] **T038** Implement HTTP request metrics (`http_requests_total{method, status}`, `http_request_duration_seconds`)
- [ ] **T039** [P] Create `src/observability/tasks.py` module
- [ ] **T040** Implement `ObservableTask` base class extending `celery.Task` with `__call__` override (Research Decision #4)
- [ ] **T041** Emit task lifecycle metrics in `ObservableTask.__call__`: `tasks_started_total`, `tasks_completed_total{status}`, `task_duration_seconds`, `task_retries_total` (FR-010)

- [ ] **T043** Configure settings `OBSERVABILITY_METRICS_ENABLED`, `OBSERVABILITY_METRICS_EXPORTER` in `src/config/settings/base.py`

### Constitutional Alignment
- **Principle II (Architecture)**: Pluggable exporter architecture via Protocol pattern (FR-014)
- **Principle VI (Performance)**: <1ms metric collection overhead; fire-and-forget emission
- **Principle V (Security)**: No sensitive data in metric labels; cardinality limits enforced

### Implementation Notes
- Use official `prometheus-client` library wrapped in abstraction (Research Decision #2)
- Per-pod metrics; Prometheus handles aggregation (FR-012a, Clarification #5)
- HTTP status grouped as 2xx/3xx/4xx/5xx (not individual codes) per FR-013
- Exception isolation: All observability hooks wrapped in try-except (FR-011a)
- Task correlation ID: Extract from Celery task headers, store in contextvar (propagation from HTTP → task)

### Parallel Opportunities
- T028/T031/T039 can proceed in parallel (different modules)
- T032/T033 can proceed in parallel with T029/T030 (exporters independent of core metrics logic)

### Dependencies
- **WP01**: Health check protocol pattern (reuse for metric collector registry)
- **WP02**: Correlation ID contextvar (task correlation ID propagation)

### Risks & Mitigations
- **Metric cardinality explosion**: Validate label values against allowlists; reject unbounded values (e.g., user IDs)
- **B15 task instrumentation breakage**: Wrap all hooks in try-except; emit `observability_signal_failure_total` on failure (Clarification #2)
- **Prometheus scrape interval**: Default 60s; document 30s option for critical services (Clarification #3)
