## Work Package WP02: Pagination Guardrails (Priority: P1) 🎯 MVP

**Goal**: Extend `BaseAPIPagination` with budget enforcement, header emission, and observability.
**Independent Test**: Request page 6 to any list endpoint → HTTP 400 with guardrail error.
**Prompt**: `tasks/planned/WP02-pagination-guardrails.md`

### Included Subtasks
- [ ] T004 Create `FetchBudget` dataclass
- [ ] T005 Add guardrail logic to `BaseAPIPagination`
- [ ] T006 Implement `X-Fetch-Budget` header emission
- [ ] T007 Add page limit enforcement with 400 response
- [ ] T008 Integrate B10 feature flags via `get_flag()`
- [ ] T009 Implement per-endpoint override resolution
- [ ] T010 Add observability logging for budget events

### Constitutional Alignment
- Principle II (Architecture): Single responsibility in pagination class
- Principle VI (Performance): No N+1 queries, early limit check
- Principle VII (API Design): Standard DRF patterns, clear errors

### Implementation Notes
- `FetchBudget` is a runtime dataclass, not a Django model
- Guardrail check happens BEFORE database query
- Budget header is JSON-encoded in `X-Fetch-Budget`
- Observability uses Python structlog

### Parallel Opportunities
- None within this package (sequential logic flow)

### Dependencies
- Depends on WP01 (settings must exist)

### Risks & Mitigations
- Breaking existing pagination → Feature flag OFF by default in tests
- Performance overhead → Benchmark <5ms per request
- Incorrect limit calculation → Unit tests for edge cases

### Acceptance Criteria (from spec)
- FR-001: `max_pages` limit enforced (default: 5)
- FR-002: `max_items` limit enforced (default: 500)
- FR-003: HTTP 400 on limit exceeded
- FR-004: `X-Fetch-Budget` header included
- FR-005: Per-endpoint overrides work
- FR-012-016: Feature flags respected
- FR-017-019: Observability logging

## Work Package WP03: Cache Headers Mixin (Priority: P2)

**Goal**: Create `CacheHeadersMixin` for ETag/Last-Modified support.
**Independent Test**: Fetch list with `If-None-Match` header → HTTP 304.
**Prompt**: `tasks/planned/WP03-cache-headers-mixin.md`

### Included Subtasks
- [ ] T011 Create `CacheHeadersMixin` class
- [ ] T012 Implement ETag generation from `max(updated_at)`
- [ ] T013 Add `If-None-Match` handling with 304 response
- [ ] T014 Implement `Last-Modified` header for detail views

### Constitutional Alignment
- Principle II (Architecture): Mixin pattern for reusability
- Principle VI (Performance): Cache support reduces load
- Principle VII (API Design): Standard HTTP caching headers

### Implementation Notes
- ETag = MD5 hash of `max(updated_at).isoformat()`
- `If-None-Match` comparison triggers 304 Not Modified
- `Last-Modified` uses RFC 7231 HTTP-date format
- Mixin applied to ViewSets that want cache support

### Parallel Opportunities
- T014 (Last-Modified) independent of T011-T013 (ETag flow)

### Dependencies
- None (independent of WP01/WP02)

### Risks & Mitigations
- ETag changes too frequently → Ensure only `updated_at` is used
- 304 not returning correct headers → Test response metadata
- Queryset evaluation cost → Use `.aggregate(Max('updated_at'))` single query

### Acceptance Criteria (from spec)
- FR-006: ETag header on list responses
- FR-007: `If-None-Match` support with 304
- FR-008: `Last-Modified` on detail responses

## Work Package WP04: Optimistic Create Support (Priority: P2)

**Goal**: Implement `X-Client-Request-ID` echo and ensure `created_at` precision.
**Independent Test**: POST with `X-Client-Request-ID` → echoed in response header.
**Prompt**: `tasks/planned/WP04-optimistic-create.md`

### Included Subtasks
- [ ] T015 [P] Create `OptimisticCreateMixin`
- [ ] T016 [P] Implement `X-Client-Request-ID` echo
- [ ] T017 [P] Ensure `created_at` millisecond precision

### Constitutional Alignment
- Principle VII (API Design): Standard headers, consistent responses
- Principle I (Product-Agnostic): Generic pattern, no product logic

### Implementation Notes
- Mixin overrides `create()` to capture request header
- Echo header in `finalize_response()`
- `created_at` already uses `DateTimeField` with microsecond precision
- Validate UUID format of `X-Client-Request-ID`

### Parallel Opportunities
- All subtasks can proceed in parallel (independent concerns)

### Dependencies
- None (independent of WP01/WP02/WP03)

### Risks & Mitigations
- Header not echoed on error → Also echo on 4xx/5xx
- Invalid UUID in header → Log warning, still echo

### Acceptance Criteria (from spec)
- FR-009: `X-Client-Request-ID` echoed on POST
- FR-010: `created_at` with millisecond precision
- FR-011: Structured validation errors
